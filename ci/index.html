ci

One copy of the CI checks, builds, and deploys, pinned by commit and audited daily across the GainRatio repositories.

Dagger 0.21.8 · Python 3.13 · no PyPI or npm release

Quickstart GitHub ↗

The problem

Between them, the repositories in the fleet need the same few things: check that the source is safe, build a Python package, and deploy a static site to Cloudflare Pages. Copying that code into every repository creates copies that drift apart. A fix lands in one place but not the others, a workflow quietly gains a step outside Dagger, and branch protection changes without anyone noticing.

ci keeps one copy as three Dagger modules, each installed at an exact commit. A daily check reads each repository’s main branch from GitHub and fails when the agreed setup has moved.

What it does

  • portfolio-foundation pins a build to one exact commit. It runs secret and workflow scans over the full Git history and wraps the build output with a record of where it came from.
  • cloudflare-pages deploys a built site once. It then checks the live site is serving that exact deployment.
  • python-package prepares the release artifacts. It audits dependencies, builds the wheel and sdist, and checks the version matches the tag. It never uploads to PyPI.
  • One thin ingress. Each workflow checks out the code and calls one Dagger function; tests, builds, scans, and deploys run inside Dagger, so the same steps run on a laptop and in GitHub Actions.
  • A daily fleet audit. fleet fails if a repository runs a step outside Dagger, branch protection has drifted, a module pin is below the reviewed minimum, main’s latest commit is not green, or a repository that installs a module is missing from the list.
  • Exact pins. Consumers install at a full 40-character commit; the fleet policy rejects main, latest, tags, and short SHAs, and upgrading is a deliberate pull request.

Quickstart

Prerequisites are Docker and exactly Dagger 0.21.8; the local gate also uses uv 0.8 or later, which fetches Python 3.13. There is no package to install from PyPI or npm: modules come from GitHub at a full commit SHA. Run this from an existing Dagger module in a consumer repository:

FOUNDATION_SHA="$(
  git ls-remote https://github.com/gainratio/ci.git refs/heads/main | cut -f1
)"
dagger install \
  "github.com/gainratio/ci/modules/portfolio-foundation@$FOUNDATION_SHA" \
  --name foundation
dagger develop

Review the captured SHA before committing. dagger install writes both source and pin into dagger.json; they must match.

To run this repository’s own gate from a clone:

git clone https://github.com/gainratio/ci
cd ci
dagger develop
uv run --directory .dagger poe gate

The full check is the same call CI makes:

export GITHUB_TOKEN="$(gh auth token)"
dagger call ci --github-token=env:GITHUB_TOKEN \
  --repository=gainratio/ci

On a branch, commit and push first, then add --commit-sha=$(git rev-parse HEAD).

A real example

In aml-filter’s dagger.json, both shared modules point at the same commit:

{
  "dependencies": [
    {
      "name": "cloudflare-pages",
      "source": "github.com/gainratio/ci/modules/cloudflare-pages@8420264d5560b0817579d9c5323ae3a69ce4558d",
      "pin": "8420264d5560b0817579d9c5323ae3a69ce4558d"
    },
    {
      "name": "foundation",
      "source": "github.com/gainratio/ci/modules/portfolio-foundation@8420264d5560b0817579d9c5323ae3a69ce4558d",
      "pin": "8420264d5560b0817579d9c5323ae3a69ce4558d"
    }
  ]
}

Before deploying, aml-filter asks whether main is green:

export GITHUB_TOKEN="$(gh auth token)"
CENTRAL_SHA=8420264d5560b0817579d9c5323ae3a69ce4558d
dagger -m "github.com/gainratio/ci/modules/portfolio-foundation@$CENTRAL_SHA" \
  call green-main --github-token=env:GITHUB_TOKEN \
  --repository=gainratio/aml-filter serialization

green-main returns typed evidence for main’s exact HEAD, including the commit SHA and Dagger check, and fails when that check did not pass.

Limits

  • Built for one maintainer’s stack. The modules assume GitHub, Cloudflare Pages, PyPI, and Dagger 0.21.8. Read and borrow under MIT, but there is no support promise, and this is not a general-purpose template catalog.
  • No reusable GitHub workflows or composite actions. The old ones were removed; they remain only in Git history and old tags.
  • No package or release publishing. python-package builds a package; publishing is a separate consumer job. The only registry writes are the GHCR image mirror.
  • No automatic upgrades. Consumers stay on their pinned commit until someone opens a pull request.
  • The fleet audit needs broad read access. Its token needs Contents, Administration, Checks, and Pull requests read on every consumer; administration read is required for branch protection and CodeQL metadata. Most contributors never run it locally.

Security and data handling

gainratio/ci holds no application data, but it reads repository state with a GitHub token, builds artifacts, and pushes OCI images to GHCR. Workflows are read-only except the image-mirror job’s packages: write. Credentials cross public Dagger functions as typed secrets; consumer candidate jobs get a read-only GitHub token, never a PyPI credential.

The source guard, full-history Gitleaks scan, and release-lineage checks are in scope for vulnerability reports. Report privately through the security policy; do not open a public issue.

FAQ

Can I use these modules in my own repository?

The code is MIT-licensed, so you can read and borrow it. The modules assume GitHub, Cloudflare Pages, PyPI, and Dagger 0.21.8, and there is no support promise.

How does a consumer upgrade?

Open a pull request that changes the commit in both source and pin in dagger.json. Nothing changes for a consumer when this repository’s main moves. The fleet policy also enforces a reviewed minimum pin for portfolio-foundation.

Does python-package upload to PyPI?

No. It audits dependencies, builds the wheel and sdist, and checks the version matches the tag. A separate consumer job publishes through PyPI’s official action; this repository never publishes a package.

What does the fleet check need?

A GitHub token that can read contents, administration, checks, and pull requests for every consumer repository. Administration read covers effective branch protection and CodeQL metadata. An unreadable repository is a failure, not a skip.

Why does dagger call ci fail on a branch?

Without --commit-sha, the history scan compares the workspace with GitHub’s main, so any change fails. Commit and push, make the tree clean, then add --commit-sha=$(git rev-parse HEAD).
