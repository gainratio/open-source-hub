EdgeReco

Product search, ranking, and recommendations that run in the shopper's browser, with no per-query backend.

Open the live demo Source on GitHub ↗

The problem

Most online stores rent search and recommendations from a service that charges per request. The bill grows with traffic, and capacity is sized for the busiest hour. Smaller stores use keyword search instead, which matches title words: type “something for my aching back” and a heating pad never appears.

EdgeReco moves search and ranking into the shopper's browser. The store publishes one signed catalog bundle — about 32.6 MB for 100,000 products — as static files. The browser verifies every chunk, streams the SQLite catalog into OPFS, and answers searches locally. With no server in the query path, there is no per-query application or inference bill, and the store works offline after the first sync.

What it does

  • Publishes a signed, content-addressed catalog. Products, an FTS5 index, quantized 384-d embeddings, and ranking weights ship as static files. The browser pins a public key and refuses a bundle whose pointer, manifest, or chunks fail verification.
  • Searches by words and by meaning. SQLite runs an FTS5 keyword match and an exact vector match, then Reciprocal Rank Fusion merges the ranked lists.
  • Updates only what changed, and runs offline. The browser diffs a new signed manifest against cached chunks and downloads only changed SQLite pages: 2 chunks, about 32 KB, in the demo's price change. After sync, the storefront works offline.
  • Re-ranks around the shopper's behavior. Views, clicks, favorites, and cart adds adjust category, tag, and brand affinity in the tab, so “Recommended for you” re-ranks without a server call. Reset taste clears the profile.

Quickstart

The browser storefront needs no Python or application server. Use Node 24.16 (see frontend/.nvmrc) and pnpm via corepack.

git clone https://github.com/gainratio/edge-reco
cd edge-reco/frontend
corepack enable
pnpm install
pnpm -F frontend run build:pages
pnpm -F frontend exec vite preview

Open http://localhost:4173 and click Launch the live demo. The demo streams the 100,000-product catalog into OPFS and loads its model on the first semantic search. Then search for something for my aching back: a neck and back massager should come first, then a stadium seat with back support, and the strip under the search box should read 0 backend calls.

A real example

To run the same engine from Python against the committed signed catalog, save this as backend/demo.py:

from pathlib import Path
from edgeproc.bundles.signing import Ed25519Verifier
from edgereco.api.deps import ServiceContainer
from edgereco.search.hybrid import reciprocal_rank_fusion

engine = ServiceContainer.from_synced(
    base_url=str(Path("examples/catalog").resolve()),
    cache_root=Path("/tmp/edgereco-cache"),
    verifier=Ed25519Verifier.from_public_bytes(
        Path("examples/keys/public.key").read_bytes()
    ),
)

query = "something for my aching back"
keyword = engine.keyword.search(query, k=30)
vector = engine.vector.search(engine.encoder.encode_query(query), k=30)

for pid, _ in reciprocal_rank_fusion(keyword, vector)[:3]:
    print(engine.by_id[pid].title)
cd backend
uv sync
EDGEPROC_ALLOW_MODEL_DOWNLOAD=1 uv run python demo.py

The script verifies the signed bundle and prints the fused top three: a stadium seat with back support, an electric heating pad, then a neck and back massager. The heating pad's title never says “back”; the vector match puts it there. EDGEPROC_ALLOW_MODEL_DOWNLOAD=1 downloads the roughly 23 MB model once; set EDGEPROC_MODEL_PATH to reuse a local copy instead.

Limits

EdgeReco is deliberately narrow. Use a hosted search service if you need millions of products or an operator, or your own server for a private catalog; you host these static files.

  • Catalog size. The demo ships 100,000 products; the design target is tens to hundreds of thousands. Search is an exact SQLite scan with no approximate index, and the whole catalog database is downloaded.
  • Public catalog data. Every shopper receives the full catalog file. Anything in it must be public.
  • Local storage. Private Browsing blocks OPFS and the demo says to reopen in a normal tab. Without a durable database, the store works but forgets activity on reload.
  • Merchandising controls. No dashboard, A/B testing, or manual boosting; ranking is tuned by editing weights in the signed catalog.
  • Proof of a result. The “why?” panel shows how a score was calculated and that the ranking settings were signed. It does not prove a specific displayed result came from those settings.

Security and data handling

The repository documents a threat model and egress inventory. The hosted demo has no analytics, event uplink, collector, or application API. Search text runs in local Workers and is not persisted.

  • The catalog fails closed: an Ed25519-signed pointer, a SHA-256-addressed manifest and chunks, and validation of ranking, vector, and co-occurrence data before import.
  • Views, clicks, favorites, and cart adds stay in a taste_events table in the shopper's on-device SQLite database: product ID, event type, and timestamp, newest 500 rows. No user ID, session ID, or PII, and nothing sends it anywhere.
  • Reset taste wipes the table and live profile; clearing site data removes everything. Export/import is not built yet.
  • Residual risks are documented: a compromised app origin can replace both the JavaScript and its pinned key, and a previously valid signed release can be replayed unless the deployment enforces freshness.

FAQ

Does the demo need a backend?

No. The catalog, model, and ONNX runtime are static files; the browser verifies and queries the catalog in-tab. The optional FastAPI server is not in the demo path.

Can I use my own catalog and signing key?

Yes. Build products with edgereco build-catalog, build the index with edgereco index, then sign and publish with edgereco bundle. Because the browser verifies against a pinned key, replace frontend/app/public/public.key with your own. The repo quickstart covers key generation.

How do I change the ranking?

The weights live in the signed ranking_config.json as bundle-carried configuration, not compiled constants. Retuning means republishing that signed data; both tiers pick it up on sync. The browser's “why?” panel shows the terms, coefficients, and contributions.

Where is shopper data stored?

Only on the device, in browser SQLite: product IDs, event types, and timestamps for the newest 500 interactions. The hosted demo sends none of it anywhere. Reset taste or clearing site data erases it; no export/import.
