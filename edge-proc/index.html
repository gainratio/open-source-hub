EdgeProc

Ship signed data to devices you don't control — each device verifies it, downloads only what changed, and can search it offline.

Source on GitHub Install from PyPI

The problem

Your app needs the same data on devices you don't control: a catalog, a price list, a search index, or a small model. The usual approach is one file on a web server, downloaded by every device.

A device cannot tell if the file was corrupted or swapped in transit, so it may quietly serve wrong answers. And one changed line makes every device re-download the whole file.

What it does

  • Publishes a signed folder. publish splits files into content-defined pieces of roughly 64 KB, names each by SHA-256, builds a manifest, and signs one small version pointer with your ed25519 key.
  • Downloads only the delta. Devices fetch only pieces missing from their cache; unchanged bytes keep their names across versions.
  • Fails closed. sync verifies the signature, manifest hash, every chunk hash, and reassembly before atomically promoting a version; any failure leaves the last good version live.
  • Handles SQLite. Publishing a .sqlite, .sqlite3, or .db file checks it, compacts it onto 4 KB pages, and zeroes header counters, so a one-row change touches only the affected piece.
  • Searches on the device. Ship a FAISS index and embedding model in the signed release; vector search can mix with BM25 keyword search, with no embedding API in the request path.

Quickstart

Python 3.13+ is required. The package is edge-proc; the import and command are edgeproc. [bundles] adds signing and sync. The demo uses local folders; no server is involved.

python3.13 -m venv .venv
source .venv/bin/activate
pip install "edge-proc[bundles]"

mkdir -p demo/src && cd demo
echo '{"p1": "red running shoes", "p2": "waterproof hiking boots"}' > src/catalog.json
edgeproc keygen --out keys
edgeproc publish --src src --origin-dir origin \
  --key keys/private.key --bundle-id catalog --version 1.0.0 --pretty
edgeproc sync --base-url origin --cache-dir cache \
  --key keys/public.key --materialize-to device --pretty
cat device/catalog.json

keys/private.key stays with the publisher; keys/public.key is the trust root for every device; origin/ is what you upload.

A real example

Publish a one-file update

Add one file and publish 1.0.1; the existing device reuses what it has.

echo 'spring price list' > src/prices.txt
edgeproc publish --src src --origin-dir origin \
  --key keys/private.key --bundle-id catalog --version 1.0.1 --pretty
edgeproc sync --base-url origin --cache-dir cache \
  --key keys/public.key --materialize-to device --pretty
published v1.0.1 manifest=18499ab39ead
synced v1.0.1 manifest=18499ab39ead chunks_fetched=1 chunks_reused=1 bytes_fetched=27

README output from edge-proc 0.5.1: one new chunk, one reused, 27 bytes over the wire. Hashes and byte counts depend on your content.

See a tampered update get refused

Corrupt one piece in the throwaway origin/ and sync to a new device.

printf 'tampered' > "origin/chunk/$(ls origin/chunk | head -1)"
edgeproc sync --base-url origin --cache-dir new-device \
  --key keys/public.key --pretty; echo "exit=$?"
[bundle.integrity_failed] sync failed: stored chunk failed to decompress
exit=1

Nothing is promoted. The healthy device keeps its active version; the new device has no active pointer, so it serves nothing rather than bad data. bundle.integrity_failed is stable; set EDGEPROC_ERROR_FORMAT=json for JSON.

Limits

  • Not a service. There is nothing to sign up for; your app and build machine run the library and CLI.
  • One-way by design. One publisher signs, many devices read. It is not two-way folder sync.
  • Can't protect a compromised host. It cannot defend an already-compromised device or build machine, or a stolen private key. Keys can be revoked, but devices learn only when you update their pinned keyring; there is no online revocation list.
  • No hard memory cap. The budget refuses new work when reserved capacity is used, but does not cap what FAISS, PyTorch, or native code allocate.
  • Search is heavy. [localvec] installs PyTorch and FAISS, about 950 MB. The default all-MiniLM-L6-v2 model's quality on your data is unmeasured; test it.
  • Linux-only CI. It is used on macOS, but Windows and macOS are not tested in CI. Version 0.5.1 is Beta.

When to use something else

Use a hosted search or vector API for always-fresh data with no device code, a plain HTTPS download with a checksum for one small, rarely changing file from a trusted server, TUF for multiple signing roles, threshold signing, or online revocation, and rsync for two-way sync between machines you control.

Security and data handling

  • Keys stay put. Publishing runs on your machine; the Ed25519 private key is never transmitted. Devices need only the public key or keyring you pin out of band.
  • Fail-closed verification. Before promotion, sync checks the signed pointer, manifest hash, every chunk's SHA-256, and reassembly. A missing trust root is a refusal, never a warning.
  • No hidden telemetry. The docs state there is no account database, analytics endpoint, or hidden telemetry. An HTTP origin sees request metadata and bundle files, not task payloads.
  • Scope. A compromised device or build machine, a stolen key before keyrings are updated, and your app's handling after verification are outside the trust boundary. The operations doc covers the threat model and key rotation.

FAQ

Do I need to run a server or create an account?

No. publish writes signed files; upload the directory to any static HTTP server or CDN, or point sync at a local folder. There is no service to operate or account to create.

What happens if a chunk is corrupted or tampered with?

The whole update is refused with a non-zero exit and bundle.integrity_failed; nothing is promoted. A good version stays live; a new device has no active pointer and no data.

How much data does an update download?

Only missing pieces. In the 1.0.0 → 1.0.1 example, adding one file fetched one chunk (27 bytes) and reused one. Content-defined boundaries mean a one-line edit usually changes one chunk; actual bytes depend on the content.

Can devices search offline?

Yes, with [localvec] and a model in the signed release. After one sync, search runs locally; by default it refuses without a local model rather than download one.
