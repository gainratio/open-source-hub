@gainratio/errors

Give every error in your JavaScript or TypeScript app one fixed code and one clear message, the same on every screen.

v0.4.0 · MIT · Node 22.13+ · zero runtime dependencies

Jump to the quickstart

The problem

Most apps write error text where the error is caught. A provider returns 402 Payment Required, and one screen says “out of credits” while another says “check your model settings”. The logs use a third wording, and the API sends a fourth. Users get the wrong advice, and nobody can search the logs for one failure.

@gainratio/errors replaces that drift with one catalog of codes for the whole app. A status, a thrown error, or a dropped connection maps to one code, one sentence, and one standard JSON body. The code never changes with language or transport.

What it does

  • One catalog. Register your codes with defineErrorsWith. Each entry has a category, an English sentence, and optional rules for an HTTP status, error name, or message text.
  • One code. classify() accepts fetch statuses, thrown errors, and network failures and returns one code from your catalog. There is no hidden global list.
  • Ready-made packs. corePack has 10 everyday codes, aiPack 9 for model providers, and bundlePack 5 for on-device files. starterPack (18) is frozen; new code should use the others.
  • Translated sentences. describe() returns the catalog's English or asks your i18next t for errors.<code>. Spanish and Brazilian Portuguese ship for all 24 built-in codes; untranslated keys fall back to English, never a raw key.
  • A standard API body. toProblemDetails() returns an RFC 9457 Problem Details object with type, title, and status.
  • Searchable logs. create() returns an Error whose .message is the code; problemFor() classifies a raw failure and keeps the observed status.

Quickstart

Install the package. It requires Node 22.13 or newer and has no dependencies:

npm install @gainratio/errors

Save this as try.mjs, a trimmed version of the repository's examples/try.mjs:

import { aiPack, corePack, defineErrorsWith } from "@gainratio/errors";

const errors = defineErrorsWith({}, corePack, aiPack);

const code = errors.classify({ status: 402 });

console.log(code);                  // ai.provider.out_of_credits
console.log(errors.describe(code)); // Your provider account is out of credits. Add credits and try again.

Run node try.mjs. The first line is the stable code; the second is the sentence from the catalog. classify() reads the status, name, and message of the raw failure. When two packs claim the same status, the one passed first wins.

A real example

Return the same error from an API

Using the errors registry from the quickstart, toProblemDetails() gives you the body to send. This is the exact output for the out-of-credits code:

const body = errors.toProblemDetails("ai.provider.out_of_credits");
console.log(JSON.stringify(body));

// {"type":"ai.provider.out_of_credits","title":"Your provider account is out of credits. Add credits and try again.","status":402}

type is the stable code, title is the sentence, and status comes from the entry's first httpStatus. Params become public fields in the body, and reserved or unsafe names are dropped.

Throw a coded error when you know the cause

If your code already knows what failed, skip classification. The error's .message is the code, so logs stay greppable:

const err = errors.create("config.missing", { field: "API_KEY" });
console.log(err.message); // config.missing
console.log(errors.describe(err.code, err.params));
// A required setting is missing: API_KEY.

When not to use it

  • It is not an error handler. It does not log, retry, report, or send anything anywhere. It classifies and formats; your app still decides what to do. Pair it with your logger or an error tracker.
  • It cannot guess a cause only your app knows. Add a code with a rule for it.
  • Descriptions are not escaped for HTML. Escape at the render site, and never put a secret in a param.
  • Browser support is not tested in CI. There are no Node-only imports, so a bundler can ship it, but the tests run on Node only.
  • For one or two error screens, hand-written messages are simpler. If you only need HTTP status to text in one language, a small switch is smaller. For collection, alerts, and dashboards, use an error tracker.

Security and data handling

@gainratio/errors is a pure library with zero runtime dependencies. It does no I/O: no network, filesystem, process, or environment access. It matches the values you pass against your catalog and returns strings and plain objects.

Codes are meant to be public and safe to log or send. Params are not: they appear in the description and Problem Details body, so keep secrets out. The library does not HTML-escape descriptions; escape them where you render. The security policy covers private reporting.

FAQ

Can I add codes for my own product?

Yes. Pass an object after the packs, or write every code yourself. An entry can set category, en, optional params, an i18nKey, and match/priority rules. The API guide shows a shop.out_of_stock code rendering “Sorry, MUG-12 is sold out.”

What happens when no rule matches?

classify() returns internal.unknown by default. Set fallbackCode to another code in your catalog; an unregistered fallback throws at startup. aiPack alone has no catch-all, so defineErrorsWith({}, aiPack) throws until you add corePack or choose one of its codes as the fallback.

Do I have to use i18next?

No. describe() accepts any function shaped like t(key, params). The package never imports i18next and never picks a language. The shipped Spanish and Portuguese JSON files are optional; your own translation function works the same way.

Which code wins when two packs claim the same status?

The pack passed first wins. defineErrorsWith({}, corePack, aiPack) sends 429 to http.rate_limited; putting aiPack first sends it to ai.provider.rate_limited. If two lists define the same code, startup throws DuplicateCodeError instead of choosing silently.
