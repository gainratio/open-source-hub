Agentic Context Service

One lookup service your AI assistants call, so each gets only the facts its job allows — with the source, version, and age of every passage.

The problem

A company with several AI assistants usually connects each one to its databases separately. Every connection re-implements who may see what. When an assistant quotes a price or a policy, nobody can tell which record it came from or how old it was.

Agentic Context Service is one HTTP service the assistants ask instead. Your databases send it each change once. For each question it removes everything that assistant may not see, searches what is left, and returns short passages. Each passage names its source record, version, and age.

What it does

  • Checks access before search. The bearer token identifies the assistant and purpose names the job. Open Policy Agent turns that into filters; a caller's filters can narrow it but never widen it.
  • Returns evidence with every passage. Each result carries a citation with the source system, record, and version, a freshness age, and a trust_class.
  • Keeps the index current and versioned. PostgreSQL changes flow through Debezium and Redpanda to an indexer, which writes them to OpenSearch. A late or replayed change cannot overwrite a newer record, and a deleted record stays deleted.
  • Searches words and meaning. OpenSearch ranks exact terms and embeddings. Requests set candidate_limit, result_limit, and max_context_tokens.
  • Refuses with stable codes. Error bodies carry a code, message, request_id, and retryable flag. A policy refusal is 403 POLICY_DENIED; a stale match under stale_behavior: "fail" is 409 CONTEXT_STALE.
  • Stores assistant memory. /v1/memories keeps memory separate from source-derived context.

Quickstart

You need git, make, and uv. uv installs Python 3.13 if needed; its installer needs curl. On a bare Linux image, install ca-certificates first. The demo needs no API key and no Docker.

git clone https://github.com/gainratio/agentic-context-service.git
cd agentic-context-service
make demo

The first run downloads Python and about 110 packages (roughly 200 MB). The demo serves http://127.0.0.1:8090/demo/ and opens the page; on a headless machine it prints the address. Stop it with Ctrl+C.

The terminal quickstart needs no browser or server:

uv run python examples/quickstart/governed_retrieval.py

It prints:

published 3 records: a pricing rule, a finance-only note, another company's rule
pricing-analysis asks "What is the discount limit for NS-100?" -> 1 result(s)
  NS-100 may be discounted at most 20% without pricing-lead approval.
  source: postgres://catalog/NS-100 v7, 90s old, trust: verified
customer-support asks "What is the discount limit for NS-100?" -> 0 result(s)

The demo is offline: the HTTP API, signature check, and access rules are the real service code, but records live in memory, matching is lexical, and a small built-in stand-in applies the OPA policies. Search by meaning needs the full local stack.

A real example

With make demo running, save this client as ask.py and run uv run python ask.py. It prints the cited passages.

import time, uuid
import httpx
from agentic_context_service.api.request_context import RequestContextSigner

KEY = b"offline-demo-signing-key-not-for-production"  # demo only

h = {
    "Authorization": "Bearer pricing-assistant-token",
    "X-Team-ID": "pricing", "X-App-ID": "pricing-assistant",
    "X-Workflow-ID": "price-check", "X-Workflow-Revision": "v1",
    "X-Agent-ID": "pricing-assistant", "X-Environment": "development",
    "X-Cost-Center": "retail", "X-Request-ID": str(uuid.uuid4()),
    "X-Trace-ID": uuid.uuid4().hex, "X-ACS-Timestamp": str(int(time.time())),
}
h["X-ACS-Signature"] = RequestContextSigner(KEY).sign(h)

r = httpx.post(
    "http://127.0.0.1:8090/v1/context:retrieve",
    headers=h,
    json={
        "query": "What is the discount limit for NS-100?",
        "purpose": "pricing-analysis",
        "corpora": ["pricing", "product", "approved-decisions"],
        "filters": {},
        "retrieval": {"mode": "lexical", "candidate_limit": 20,
                      "result_limit": 3, "max_context_tokens": 2000},
    },
)
r.raise_for_status()
for result in r.json()["results"]:
    citation = result["citation"]
    print(result["text"])
    print(f"  from {citation['source_uri']} version {citation['source_version']}")

It prints:

NS-100 discount limit: at most 20% off list price without pricing-lead approval.
  from postgres://catalog/pricing_rules/NS-100 version 7
NS-100 is a waterproof trail running shoe, sizes 6 to 13, list price $120.
  from postgres://catalog/products/NS-100-product version 3
Approved promotion: NS-100 is 15% off until October 31. Support may quote this price.
  from postgres://decisions/promotions/PROMO-88 version 1

In production the API gateway holds the key and signs the request, so assistants never see it. The repository's examples/client/ask_the_service.py is the fully commented client.

Limits

  • Beta. Version 0.1.0 has no tagged release and is not on PyPI; install it from the repository.
  • Not a chat app or a framework for building assistants. It is the lookup your assistant calls.
  • One assistant out of the box. The stock entry point accepts one token, ACS_DEMO_TOKEN. To give each assistant its own identity, implement BearerAuthenticator and pass it to create_app from your own entry point.
  • Not the source of truth. Your databases are. The index updates a moment after a database change, not in the same transaction.
  • The local stack is for trying it, not production. It turns off TLS, private networking, and OpenSearch's per-document security. There is no high availability, backup and restore, or load testing yet.
  • It cannot protect a compromised server or operator, or control what an AI provider does with data you send it.

Security and data handling

The service runs on your machines. Source-derived content and memory stay there; nothing leaves unless you turn on the optional live AI mode (ACS_SHOWCASE_AGENT_MODE=deep) in the full-stack dashboard.

Requests are signed: a bearer token identifies the assistant, purpose names the job, and 11 headers are canonicalized and signed with HMAC-SHA256. Signatures older than five minutes or more than 30 seconds ahead are refused; the key must be at least 32 bytes. The gateway holds it in production.

Policy fails closed. OPA constraints are applied before search, caller filters intersect them, and an OPA outage or malformed answer makes readiness false.

The threat model records what is protected and what is not: raw tokens stay out of OPA and audit logs, and queries are hashed. Compose disables OpenSearch security and uses visible synthetic credentials; it is local-only, not a deployment template.

FAQ

Do our assistants have to be written in Python?

No. They send one POST /v1/context:retrieve. The Python package ships the server and a local signer; other languages compute the same HMAC-SHA256 over the 11 canonical headers.

How does the service decide what an assistant can see?

The bearer token identifies the assistant, and purpose names the job. OPA turns that pair into constraints applied before ranking; caller filters can narrow but never widen them, and a request outside the job's scope returns 403 POLICY_DENIED.

Is the search index the system of record?

No. Your databases are. Changes reach OpenSearch a moment after the database commit; the index is derived, not authoritative.

Can we search by meaning, or store assistant memory?

Both are in the full service: OpenSearch handles semantic retrieval and /v1/memories stores memory. Neither is available in the offline demo; the terminal quickstart is lexical only.

Is it production-ready?

Not yet. It is Beta 0.1.0. Compose is local-only with no high availability, backup and restore, or load testing.
