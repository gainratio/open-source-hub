AML-Filter

Screen customer names against four sanctions lists in your browser, see why each match scored, and keep the customer records on your machine.

The problem

Businesses that have to know their customer must check names against sanctions lists. Large firms buy a screening vendor; small ones search government sites by hand and keep notes in a spreadsheet. The vendor costs money and receives a copy of the customer list. The manual route is slow, and a name spelled a little differently is easy to miss.

AML-Filter is a static web app that does the check in the browser tab. It downloads a signed copy of the public lists, matches names locally, and shows the evidence behind every result. There is no account, screening server, or upload of the names you type.

What it does

  • Screens against the US OFAC SDN, EU consolidated, UN consolidated, and UK asset-freeze list, and names the source list on every result.
  • Matches by meaning with an in-tab MiniLM embedding, by spelling and phonetic similarity, and by aliases. Date of birth and country are optional signals.
  • Returns a 0–1 score with the five signal contributions (name_vector, name_sequence, alias_match, dob_match, country_match), a plain-language explanation, and STRONG/POSSIBLE/WEAK tiers. A person makes the call.
  • Verifies the watchlist before screening: an Ed25519-signed pointer, SHA-256 content hashes, and a pinned same-origin key. A bad signature or hash aborts the load, whether fetched or read from cache.
  • Adds a local KYC workflow: import customers from CSV, XLS, or XLSX, screen them on onboarding, record decisions in an append-only event trail, and re-screen when a list or customer changes.

Quickstart

You need Node 22.13.0 exactly (see frontend/.nvmrc) and pnpm 11.5.0, which corepack provides. Install and run from frontend/; there is no root package.json.

git clone https://github.com/gainratio/aml-filter.git
cd aml-filter/frontend
corepack enable
pnpm install
pnpm --filter aml-filter-app dev

Open http://localhost:5173/screen. Use localhost, not a LAN address: the signature check needs a secure context.

Minimal example: enter fakovic. The committed demo list returns one match, Ivan Fakovich, score 0.547. That list contains eight made-up people, not real sanctions data. Use the hosted app for the four real lists.

A real example

On the live app, screen Vladimir Putin. The README records the top result as Putin Vladimir Vladimirovich on the US OFAC SDN list at 0.952. Open Why this score? to see the signals that drove it: the names are close in meaning and spelling, and PUTIN, Vladimir is a listed alias.

To inspect the data the live app is running on, fetch the signed pointer and the pinned key:

curl -s https://aml-filter.com/bundle/origin/latest
curl -s https://aml-filter.com/public.key | od -An -tx1

The pointer carries version, sequence, manifest_hash, and signature. The key bytes should match frontend/app/public/public.key. The app trusts that pin, not a key carried inside the bundle.

Limits

  • Not a compliance product or legal advice. A qualified person must confirm each possible match against the official source; a no-hit result is not a safe harbour.
  • Sanctions lists only. No politically exposed persons, news searches, or company ownership.
  • One person, one browser. There is no shared team queue and no cross-device sync. Clearing site data deletes the customers and decisions; the XLSX export covers the customer table only.
  • Online only. Verified chunks are cached for repeat visits, but there is no service worker and no offline mode.
  • Close misspellings, not wild ones. Vladimir Poutine still finds Putin, but as the second result. Read the whole list, not just the top line.
  • Browser coverage. Current desktop Chrome, Edge, Firefox, and Safari 17+; phones use a lower-memory mode.

Security and data handling

  • Pinned trust root. The Ed25519 public key is served same-origin and pinned in the build. Ed25519 verifies the signed pointer; SHA-256 verifies the content-addressed manifest and every chunk before use. Cached bytes are re-checked, and a mismatch aborts the load.
  • Local customer data. Names, dates of birth, customer records, and decisions stay on the device, in SQLite-WASM over OPFS. There is no account, server-side screening endpoint, analytics script, third-party font, or error beacon.
  • One network destination. The app fetches its own assets and the public list bundle. Downloading public sanctions data reveals nothing about who you are screening.
  • Not tamper-evidence. The review history is append-only during a customer's lifetime, enforced by SQLite triggers, but the database is a local file with no hash chain; an operator can drop the triggers. Use a centrally retained record if your process requires one.
  • Key history. SECURITY.md records a 2026 production signing-seed exposure and rotation; do not roll production back to a build from before 2026-07-21.

FAQ

Is AML-Filter a compliance product?

No. It is open-source screening software, not legal advice or a certified compliance product. It can be one control in a process; a qualified person must still confirm matches, and your own regulatory obligations still apply.

Does it work offline?

No. There is no service worker, so the tab needs the network to load. The verified bundle is cached in OPFS and re-verified on each load, so repeat visits download only changed chunks.

Where do customer records live?

In the browser's origin-private file system, in a SQLite-WASM database. They are not uploaded and do not sync to another browser or device. Clearing site data deletes them; the spreadsheet export contains the customer table, not the match decisions.

How fresh are the sanctions lists?

The publisher rebuilds the lists daily. While the app is open it checks for a newer signed bundle every 30 minutes, or on demand from the Customers page. It shows the version and last update, and reports a source it could not download instead of pretending the list is current.

What does a match score mean?

A 0–1 similarity score, where higher means closer. It is not a pass/fail result. It shows which signals fired and tiers matches STRONG, POSSIBLE, or WEAK. Read the reasons and other results, not just the top line.
