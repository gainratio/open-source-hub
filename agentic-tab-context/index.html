The problem

Most browser automation starts a fresh browser with no session, no login and no half-finished checkout, so the page you need is out of reach. Copying page text, screenshots and console output into chat is slow and loses what matters.

Agentic Tab Context connects your coding assistant to the browser you already use. You share a tab, the assistant runs a local CLI called atc, and the chat stays where it is.

What it does

  • Binds a tab to a context. atc tabs lists tabs with stable IDs; atc bind returns a context for later commands.
  • Reads the page as an outline. atc inspect returns visible headings, links, buttons, fields and dropdown options in YAML style. Password values are omitted.
  • Acts on one exact element. Element commands take one locator, match only visible elements, and report the match count plus an effect such as url_changed.
  • Shows what the page did. atc console and atc network return entries with a --since cursor; atc screenshot saves a viewport PNG, with --redact masking password, one-time-code and card fields.
  • Shares tabs as a workspace. The side panel shares, unshares and locks tabs and sets the active target; atc bindings lists contexts and atc use switches. Managed windows need no share.
  • Fits your assistant. One JSON line per command, exit 0 only when ok is true. The installer writes skills for Claude Code, Codex and Antigravity.

Quickstart

You need macOS or Linux, Git, Node.js 22+ with npm, and Chrome or another Chromium browser; open it once before installing. Windows stops before writing files.

git clone https://github.com/gainratio/agentic-tab-context.git
cd agentic-tab-context
./install.sh

The installer builds the CLI, links atc globally, installs the skill and registers the browser bridge. Keep the clone in place; the CLI reads files inside it.

Then load the extension at chrome://extensions: enable Developer mode and choose Load unpacked for the extension folder. Run atc doctor; extension.connected should list your browser.

Share a tab from the side panel, then bind and inspect it:

atc bind "localhost"
atc inspect

bind creates the context; inspect reads that tab. Your assistant runs these; running them yourself confirms the connection.

A real example

The workflow this project targets is a local checkout that fails after Pay. Bind the exact page, then read before acting:

atc bind --url "http://localhost:3000/checkout"
atc inspect
atc click --role button --name "Pay"
atc console --since 0
atc network --since 0

inspect supplies the exact button name click needs. The click reports whether the URL or title changed; an error without navigation appears in console entries and failed requests. Both buffers clear on unwatch, close or navigation.

Then a demo signup form, typing only the values you pass and capturing a redacted screenshot.

atc bind --title "Signup"
atc type --label "Email" --value "a@b.co"
atc select --label "Plan" --value "Pro"
atc click --role button --name "Create account"
atc screenshot --redact --out /tmp/signup.png

If a click matches several buttons it fails with AMBIGUOUS_TARGET; re-inspect, narrow the locator, or add --nth.

Limits

  • Install is from a clone. The npm package is private and no store build is published, so there is no npm install -g or store step; the clone must stay in place.
  • Browser coverage is uneven. Chromium is tested automatically and Chrome 155 on macOS was tested locally. Brave, Edge and Firefox are untested; Safari is discovery only because it has no stable tab identity. Without the extension on macOS, Chrome, Brave and Edge need Apple Events and cannot take screenshots.
  • Live screenshots are viewport-only. --full-page returns UNSUPPORTED_ACTION for a live tab.
  • Targeting is strict. Every element action needs one visible match, iframes are unsupported, and pages under an older page agent may need a reload and rebind.
  • Everything runs locally. The assistant must be on the same machine as the browser; there is no remote relay.
  • Some state persists. Contexts live in state.json under ATC_HOME (default ~/.atc) with no TTL; atc upload takes a path up to 8 MiB.

Security and data handling

The bridge is local. The daemon listens on owner-only Unix sockets under ATC_HOME (mode 0600), checks a per-install token and opens no network port. The extension uses native messaging and sends nothing to GainRatio or third parties; there is no tracking.

The extension sees the titles and addresses of open tabs and reads page content only while a tab is bound. Password values are omitted from inspection and atc type values are scrubbed from errors. Other page text and logs can still contain secrets; screenshots are unredacted unless --redact is passed. Page content is untrusted and can carry prompt-injection text, so treat it as data, not instructions; your assistant's handling follows its own terms.

Screenshots, state and profiles stay under ATC_HOME after extension removal; atc shutdown stops the service.

FAQ

Does it use my existing logins?

Yes. It drives the profile you already use, so you log in yourself; atc open chromium starts a separate managed window.

Why does atc bind return TAB_NOT_SHARED?

Extension tabs must be shared from the side panel before binding; bind never grants access. Managed tabs need no share.

Do I need an MCP server or a cloud account?

No. The installer writes skill files and registers the local bridge. Optional tools like Chrome DevTools MCP are separate; this project does not install them.

Which browsers can it actually drive?

Chrome and Chromium with the extension are the tested path; the Limits section lists the untested browsers.

How do I remove it, and what stays behind?

Run atc shutdown, unlink the package, remove the extension, and delete the native-host manifests and skill files from setup output. Keep ~/.atc for managed logins and screenshots, or delete it to remove those too.
