AlmaMesh

Your Vedic birth chart, computed in your browser by an open Python engine — no account, no chart-data server.

The problem

Most astrology sites calculate on a server. You hand over a name, an exact birth time and a birthplace, then receive a chart you cannot inspect. Those details are identifying and do not change, so where it runs and what is kept matter as much as the result.

AlmaMesh moves the calculation into the tab. The app is a static PWA; the engine is an open Python package, delivered as a signed bundle and run in a Web Worker under Pyodide. Birth details go from the form to that worker; the chart is stored in the browser.

What it does

  • Draws a sidereal kundli — the nine grahas, whole-sign houses, the rising sign, and each planet's nakshatra and pada — in degree-accurate North and South Indian styles. The free kundli page uses the same engine.
  • Lays out timing: Vimshottari dasha at maha, antar and pratyantar levels; Gochara transits and Sade Sati; D1–D60 divisional charts; Ashtakavarga and Shadbala. The dasha page breaks down the periods.
  • Rectifies an uncertain birth time from dated life events. The accepted time becomes the chart authority; rejected candidates never feed transit houses or the report.
  • Finds muhurta windows from nakshatra, tithi and weekday suitability plus the running periods; the muhurta page describes the report.
  • Reads two charts together in the mesh — Ashtakoota Guna Milan for partner edges, chart overlay, dasha synchrony and significators — as a frozen, read-only result. Kundli matching is the live entry point.
  • Keeps named, password-less profiles and charts in one on-device SQLite database, with an encrypted .almamesh export/import, a deterministic PDF report, time travel, and English, Spanish and Portuguese text. It installs as an app and works offline after first load.

Quickstart

Source builds need uv and Bun; uv fetches Python 3.13. Clone and build:

git clone https://github.com/gainratio/almamesh.git
cd almamesh
make demo

make demo installs the workspaces, signs a local dev bundle with a throwaway key, builds, and opens http://localhost:4173. Use the built app, not bun run dev: the engine's module workers need a production build. The first chart downloads about 38 MB of engine, cached offline.

The same engine without a browser:

cd backend
uv sync --extra dev
uv run almamesh-chart "1990-01-15T12:00:00+00:00" 40.7128 -74.0060

It prints the chart as JSON.

A real example

The README's New York example returns:

{
  "ayanamsa_value": 23.7174,
  "lagna": {
    "longitude": 264.9083218673543,
    "sign": "Sagittarius",
    "sign_degrees": 24.90832186735429,
    "sign_lord": "jupiter",
    "nakshatra": "Purva Ashadha",
    "nakshatra_pada": 4,

lagna is the ascendant, Sagittarius 24.91° here. The rest lists planets, houses and dasha periods. The result is a pure function of its three arguments except for the current_* fields: the CLI has no reference-date option, so those use the day you run it. The app records a reference instant with every chart; that fourth input makes CPython and Pyodide return identical bytes.

To check the astronomy, run the committed oracle tests — no network, no live API:

cd backend
uv run pytest tests/validation/test_ground_truth.py tests/test_transit_reference.py -q

Agreement with astropy and JPL Horizons references is about 0.05 arcsec; the natal gate allows 18 arcsec for planets and 180 for the ascendant, and the transit gate allows 1 arcsec.

Limits

  • It does not predict events. A retrodiction eval ranked real life-event months from licensed birth records and found no lift over chance (best corrected p-value 0.80). How we test says readings are for reflection; strength percentages are structural measures, not validated outcomes.
  • Birth time still matters. Rectification ranks candidates and reports a fit margin; that margin is not the probability that a birth time is correct.
  • Browser parity is natal-only. The transit, predictive and mesh goldens are enforced on CPython, but their Pyodide parity is not browser-gated yet.
  • No account, no sync. Moving browsers means exporting the passphrase-encrypted .almamesh file and importing it. The on-device database is not encrypted at rest.
  • AI is optional and constrained. It is off by default; a custom OpenAI-compatible endpoint must be loopback, or use the OpenRouter preset. A LAN address or third-party proxy is refused by the Content-Security-Policy. No chart needs it.

Security and data handling

The README's network inventory is enforced by the app:

  • The chart engine is zero-egress. During birthplace search the city text goes to Open-Meteo; a bundled city list is the offline fallback. With AI enabled, PII-redacted chart facts — planet positions and month-precision period dates — go to your configured endpoint, which can still reveal a birth date and approximate time. Profile names and the birth-date field are not sent.
  • The engine bundle is verified before use: Ed25519 signature against a same-origin key, SHA-256 for the manifest and each chunk, and a signed increasing sequence that rejects rollback. A mismatch stops boot and offers reset rather than running unverified code.
  • The Content-Security-Policy limits connect-src to this origin, openrouter.ai, geocoding-api.open-meteo.com and loopback, so another destination is refused by the browser.
  • Not protected: a compromised device, browser or extension; a compromised almamesh.com origin (the verification key is delivered from it); or what Open-Meteo and your AI provider do with what you send.

FAQ

Why doesn't bun run dev show a chart?

The engine is a module Worker and needs a production build. Run bun run build && bun run preview in frontend/apps/web, or use make demo.

Why does a single pytest file fail the coverage check?

addopts enforces a 90% coverage floor on every run. Add --no-cov for one file: uv run pytest tests/test_navamsa.py -q --no-cov.

Can I self-host it?

Yes. The origin is static files plus a signed bundle and key. almamesh-bundle keygen and almamesh-bundle bundle create them; VITE_BUNDLE_BASE_URL points at another bundle origin. A dev key will not match production, by design.

Is there an AlmaMesh package to install?

No app package is published; clone the repository and run make demo.

What licence applies?
