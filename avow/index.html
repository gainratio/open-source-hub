Avow

Sign a JSON record into a receipt anyone can check offline — unchanged, and signed by the key you pinned.

Install and sign a record

The problem

Teams often have to show later what they decided: that a release was approved, that its tests passed, that a setting was what they claim. That record usually sits in a database or log the team controls, so an auditor or customer must take their word that nobody edited it. A plain checksum does not settle it, because whoever edits the record can recompute the checksum.

Avow puts a signature on the record. You keep a private key and hand out the matching public key once, ahead of time. The receipt carries the record, its fingerprint, and a signature; a verifier holding that public key can check it on their own machine. If one word changed, verification refuses it.

What it does

  • Canonicalizes before hashing. RFC 8785 gives JSON one fixed form — sorted keys, no extra whitespace, one number spelling — so the same data always yields the same bytes. Avow takes a SHA-256 fingerprint of those bytes and signs the canonical bytes with Ed25519.
  • Produces a self-contained receipt. The avow.receipt/v1 envelope holds the plain-text payload, its fingerprint, the signer's public key, and the signature.
  • Pins the signer. Verification recomputes the fingerprint and requires the signer to equal the public key the caller supplies, never the public_key stored in the receipt.
  • Refuses with stable codes. An altered payload returns avow.payload_hash_mismatch; a different signer returns avow.signer_mismatch. Commands exit 2, or 3 when a ledger needs recovery.
  • Ships two implementations. Python provides the library, command, and ledger; @gainratio/avow reads and writes the same receipts from TypeScript, held together by shared test vectors.
  • Can chain receipts. The Python ledger verifies each receipt, their order and links, and a final head. With the head pinned out of band, deleted, inserted, reordered, or truncated entries are caught.

Quickstart

Requires Python 3.12 or newer. Install the library and the command:

pip install "avow[cli]>=0.5.3"

Generate a key, sign a decision record, and verify it:

avow keygen --out signing.key
echo '{"release": "checkout-api 2.4.1", "approved_by": "dana", "tests_passed": true}' \
  > decision.json
avow sign --payload decision.json --key signing.key --out receipt.json
avow verify --receipt receipt.json --public-key signing.key.pub

It prints:

avow.keygen.ok
avow.sign.ok
avow.verify.ok

signing.key is private; keep it. signing.key.pub is the key to give verifiers through a channel they already trust. pip install avow is the library alone; npm install @gainratio/avow (Node.js 22.13 or newer) is the TypeScript package. Current release: 0.5.3.

A real example

The repository's evidence loop signs a deployment decision, not a toy string. This trimmed version signs it, verifies it, then changes the outcome in a copy:

from avow import generate_signing_key, public_key_hex, sign_payload, verify_receipt
from avow.errors import AvowError

decision = {
    "schema": "deployment-decision/v1",
    "service": "checkout-api",
    "environment": "production",
    "artifact": {"source_commit": "9f37c2a"},
    "decision": {
        "outcome": "approved",
        "policy": "release-policy/v3",
        "checks": ["unit-and-integration-tests", "dependency-audit", "staging-smoke-test"],
    },
}

signing_key = generate_signing_key()
verifier_key = public_key_hex(signing_key)
receipt = sign_payload(decision, signing_key)
verify_receipt(receipt, expected_public_key=verifier_key)

altered_payload = {**decision, "decision": {**decision["decision"], "outcome": "rejected"}}
altered = receipt.model_copy(update={"payload": altered_payload})
try:
    verify_receipt(altered, expected_public_key=verifier_key)
except AvowError as error:
    print("refused:", error.code)

The first check passes; the second prints refused: avow.payload_hash_mismatch. The edited payload no longer matches its stored fingerprint, so verification refuses before checking the signature.

Limits

  • Not proof of truth, freshness, or time. A receipt proves integrity and that the expected key signed it, not that the record is correct, complete, current, or timestamped.
  • Not replay protection. A valid receipt verifies every time it is presented. If reuse matters, put a nonce, audience, and expiry inside the signed payload and check them after verification.
  • Keys are files, not a service. The private key is an unencrypted Ed25519 seed protected only by file permissions; there is no passphrase, KMS, or HSM support. Anyone who copies it can sign as you.
  • The ledger needs an outside pin. A head file beside the ledger is convenient, not authoritative. If an attacker can rewrite both, truncation is not caught; store the head elsewhere.

Use something else when you only need to catch accidental corruption (a checksum), you sign files for people who already use GPG, minisign, or ssh-keygen -Y sign, you need public time-stamped release signing (Sigstore or a transparency log), or you need login or API tokens (a JWT/JWS library).

Security and data handling

Avow's runtime opens no socket and calls no remote service. Signing, verification, and ledger work are local file and cryptographic operations; there is no telemetry, upload, timestamp server, key server, or background process. Installing dependencies may use your package manager's network, which is outside Avow's runtime boundary.

Receipts carry their payload in cleartext, and ledgers are local JSONL; keep secrets out. Access controls, backups, retention, deletion, and export are the integrating application's job. Distribute the public key out of band.

On POSIX, key generation writes an owner-only 0600 file, and signing refuses a key that group or others can read with avow.key_permissions_insecure. The TypeScript package never reads key files, so the application stores the seed. Releases carry PyPI and npm provenance; check the attestation for the version you installed, or build from a reviewed commit.

FAQ

Does verification need a server or a network connection?

No. The receipt and a public key obtained separately are enough; the check is local math.

What happens if someone edits the payload or presents a receipt signed by another key?

An edited payload fails the fingerprint check with avow.payload_hash_mismatch. A receipt signed by a different key fails the signer pin with avow.signer_mismatch. Both are stable codes, not warnings.

Can TypeScript verify a receipt produced by Python?

Yes. Both packages read and write the same receipt format and are checked against shared test vectors. The ledger and key-file loading are Python-only; TypeScript takes a caller-held seed instead.

Does Avow prevent replay or provide a trusted timestamp?

No. Avow keeps no nonce, audience, expiry, or clock state, so a valid receipt verifies identically every time. Callers that need freshness sign those claims into the payload and enforce them after verification.
