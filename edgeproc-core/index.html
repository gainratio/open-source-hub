edgeproc-core

Keep each tenant’s vector search results separate in a shared or bucketed index, and turn raw failures into stable codes.

v0.4.3 beta · Python 3.13+ · MIT

View source on GitHub Install from PyPI

The problem

Any product with “find similar” or document search stores every customer’s embeddings in one place. One index per customer is simple, but wastes memory at thousands of customers. One shared index is cheaper, but every search, count, and delete must carry the owner filter. Miss it once, and a customer sees — or deletes — someone else’s rows.

Failures repeat the pattern: an HTTP 402, a timeout, and a browser’s “Failed to fetch” arrive as different objects, so every layer writes its own if-ladder. edgeproc-core ships two independent modules for this plumbing; they do not import each other.

What it does

  • Routes by owner. Tag a vector with its tenant, user, org, or any metadata key. The strategy picks one global index, one of N hash buckets (256 by default), or a hot/cold tier by created_at.
  • Scopes every call. search, delete, and get_stats pass the owner as a filter, so a scoped caller cannot read, count, or destroy a neighbour’s rows. Multi-index results are merged into one ranked list.
  • Keeps the store yours. Implement the small VectorIndex protocol over FAISS, pgvector, hnswlib, or an internal system. The only shipped index is an in-memory reference for tests and examples.
  • Tests the safety property. assert_vector_index_conformance seeds two owners into one physical index and raises with the property your backend broke.
  • Standardises errors. The separate edgeproc_core.errors module has 18 starter codes plus classify, describe, and RFC 9457 Problem Details, matching TypeScript @gainratio/errors.

Quickstart

Requires Python 3.13 or newer. The README’s tested path uses uv, which can fetch Python 3.13:

mkdir try-edgeproc-core && cd try-edgeproc-core
uv venv --python 3.13
uv pip install edgeproc-core

With Python 3.13 installed, pip install edgeproc-core works too. Save this as example.py; both customers store an identical invoice in one physical index (num_buckets=1), the hardest case for isolation:

import asyncio
from edgeproc_core import BucketedPartitionStrategy, IndexManager, VectorEmbedding
from edgeproc_core.errors import define_errors, starter_pack
from edgeproc_core.vector_mgmt.testing import in_memory_factory

async def main() -> None:
    manager = IndexManager(
        BucketedPartitionStrategy(
            index_factory=in_memory_factory,
            num_buckets=1,
        )
    )
    for owner in ("acme", "globex"):
        await manager.insert([
            VectorEmbedding(
                entity_id=f"{owner}-invoice",
                embedding=[1.0, 0.0],
                metadata={"tenant_id": owner},
            )
        ])
    print("acme sees:", await manager.search([1.0, 0.0], k=10, partition_key="acme"))
    print("no filter:", await manager.search([1.0, 0.0], k=10))

asyncio.run(main())
errors = define_errors(starter_pack)  # 18 ready-made error codes
print(errors.to_problem_details(errors.classify({"status": 402})).to_dict())

Run it with .venv/bin/python example.py:

acme sees: [('acme-invoice', 0.0)]
no filter: [('acme-invoice', 0.0), ('globex-invoice', 0.0)]
{'type': 'ai.provider.out_of_credits', 'title': 'Your provider account is out of credits. Add credits and try again.', 'status': 402}

The scoped search returns only acme’s invoice; the unscoped search is the deliberate admin view and returns both. The last line turns {"status": 402} into ai.provider.out_of_credits Problem Details.

A real example

Prove your backend applies the filter

The conformance suite is a plain coroutine, so it works with or without pytest. This runs against the bundled reference index; replace the factory to grade your own backend:

import asyncio
from edgeproc_core.vector_mgmt.conformance import assert_vector_index_conformance
from edgeproc_core.vector_mgmt.testing import in_memory_factory

# Swap in_memory_factory for a factory that returns your VectorIndex.
asyncio.run(assert_vector_index_conformance(in_memory_factory))

It seeds two partitions into one index and gives every row the same vector, so ranking cannot separate them. The thirteen checks cover scoped and unscoped search, delete, and stats, including a delete that must spare the neighbouring partition. Recall, latency, and rebuild() are not graded.

Limits and when not to use it

  • No production index ships. It is not a search engine or durable store. InMemoryVectorIndex is for tests and examples; you bring FAISS, pgvector, hnswlib, or your own.
  • It is not access control on its own. A partition key is a routing hint, not a security principal. If your backend ignores filters, tenants leak; enforce authorization in the database too.
  • Unscoped calls are administrative. With no partition key, search, delete, and get_stats span every owner. Keep that path away from end users.
  • It does not measure your backend. Recall, latency, memory, backups, and retention belong to your store.
  • 0.4.3 is beta. The API may change before 1.0. The error module is unrelated to the vector code.

Use one index per customer if you have a few large customers and can afford it, or your vector database’s built-in multi-tenancy if you are committed to one store. Choose edge-proc for search on devices with signed downloads.

Security and data handling

docs/OPERATIONS.md and SECURITY.md document the trust model. The library is in-process: no network or filesystem I/O, no telemetry, and no cloud fallback. Embeddings, metadata, keys, filters, and query vectors move only from your process into your VectorIndex.

Partition names are routing hints, never security principals; bucket collisions are expected, so enforce access in the backing store. The in-memory index retains embeddings until delete, exit, or disposal, and deletion tombstones an ID. Retention and backups belong to your backend.

Releases are built from a pinned main commit and published to PyPI with trusted publishing and attestations. Supported versions are >=0.4.3; report vulnerabilities through the private advisory (48-hour acknowledgement, seven-day assessment).

FAQ

Does the partition filter make my application multi-tenant-safe?

No. The key must come from authenticated identity, the backend must apply filters with AND semantics, and the database should enforce row-level access.

Can I use user_id or a composite key instead of tenant_id?

Yes. Set partition_key_name="user_id" on the strategy and manager and store it in metadata; composite keys use a partition_key_extractor. Legacy tenant_id works.

How do I know my backend is filtering, not just type-checking?

Run assert_vector_index_conformance. It writes two partitions into one index with identical vectors and checks search, delete, and stats, including cross-partition deletes, raising an AssertionError for each broken property.

Why does a search library ship error codes?

edgeproc_core.errors solves a separate problem: one stable code across API, UI, and logs. It has 18 starter codes, classifies raw failures, and serialises RFC 9457 Problem Details matching TypeScript @gainratio/errors. Problem Details members are public; never pass secrets as params.
